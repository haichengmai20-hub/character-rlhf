## Q01｜你个人完成了哪些关键技术工作？

**面试官实际在检查：** 能否把项目介绍落到自己参与的具体判断，而非只复述一条完整 Pipeline。

**主答**

我会围绕一个技术闭环讲贡献：发现什么问题，怎样把问题变成可观测指标，比较了哪些解释，最后改了什么，以及如何验证。ChatJoy 的主线是将“角色不稳、语言错配、富度不足和破角”拆成可生成性、偏好排序、Reward 合成与 Actor 更新四层问题。

例如，围绕“奖励上升但角色行为变差”这个问题，技术工作不是笼统地说调了 RL，而是固定候选检查 RM 排序，逐条核对 RM、规则和最终 Reward，再检查同 Prompt 优势与外部行为指标，找出错误被放大的环节。这个闭环能体现算法、数据与工程的结合。

个人回答要挑自己实际负责的一段，展开到字段、函数或产物；其他部分说明自己承担的是设计、实现、实验分析还是协作对接。现有资料没有完整团队分工，因此不能从“项目中有这个模块”自动推出“都是我独立完成”。

**连续追问**

- **“如果只能讲一个最有价值的改动，你选什么？”**  
  选择自己掌握证据最完整、决策最明确的一项。比如 Reward 对账、偏好数据准入或 score head 保存问题，讲改动前后的机制差异与验证，不用堆框架名。
- **“你与调用开源框架的区别在哪里？”**  
  说明业务目标如何转成数据和损失接口，以及哪个默认假设不适用于本项目；没有改框架源码也可以有算法贡献，但要具体到判断与实现。

**易失分回答：** “整个项目都是我做的”，随后无法说明一条样本如何进入 Loss。

来源：[全链路总览](../00_ChatJoy后训练全链路统一面试复习.md)、[项目技术复习](../RL/01_RL完整流程与关键机制演进.md)。

## Q02｜这个项目最终改善了什么业务问题？

**主答**

业务对象是多语言角色对话。质量不只取决于“是否回答”，还包括能否使用目标语言、持续符合角色、承接历史、推进互动，以及受到角色覆盖攻击时保持合理行为。

因此我把指标分成能力、红线和成本三类：能力看角色、语言、推进、有效表达；红线看真实破角、系统泄露、严重退化；成本看推理延迟、每次会话的资源开销和维护复杂度。Clean 的平均分提高，不能抵消 Attack 红线恶化。

离线评测回答“固定协议下的行为是否改善”，线上抽样回答“真实流量有哪些未覆盖问题”。它们可以互相补充，但不能仅凭离线分数推断留存、付费或满意度提高；这些产品指标需要对应的线上观测或实验。

**连续追问**

- **“没有线上 A/B，还能说有价值吗？”**  
  可以准确报告受控离线行为、产品 Bad Case 修复和工程成本变化；商业指标的因果收益需要另有证据。技术收益不必夸大成商业收益。
- **“角色、富度、破角相互牵制，如何决定上线？”**  
  先用不可补偿的红线门排除不合格方案，再比较开放质量和成本。关键切片分别验收，不只选总分最高的模型。

**易失分回答：** 用“用户更喜欢”代替具体指标，或者把训练 Reward 当成用户满意度。

来源：[Benchmark 专题 §2、§5](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q03｜为什么采用 SFT→RM→RL，而不是继续 SFT、直接 DPO 或 Best-of-N？

**主答**

我先判断瓶颈在哪一层。模型缺少目标行为时，SFT 能提供明确示范；同一 Prompt 已能生成好坏候选但选择不稳定时，偏好学习开始有价值。RM 学习相对质量，RL 用当前策略产生的数据调整生成概率。

DPO 可以直接用偏好 Pair 更新策略，省掉独立 RM 与在线 Rollout 的一部分复杂度，适合偏好数据较稳定、离线分布足够覆盖目标场景的情况。它不因为没有独立 RM 就免疫标签噪声或分布偏移，仍需要外部评测。

Best-of-N 把成本留在推理时：每次多生成、多打分，再选择。若业务可以承担额外延迟与费用，它是应当比较的方案。RL 则希望把偏好更多内化为单次生成行为，但增加训练系统和稳定性成本。选择 RL 必须说明在线候选变化、业务推理预算和预期收益，不能只因为 Pipeline 看起来完整。

**连续追问**

- **“为什么不持续增加高质量 SFT？”**  
  若目标行为仍缺失，继续 SFT 很合理；如果行为已经有覆盖，主要问题是相对偏好，偏好优化可能更直接。通过候选 Support、排序正确率和最终生成评测区分。
- **“SFT 模型里几乎不会出现某个答案，RL 就绝对学不到吗？”**  
  不是数学上的绝对不可能，而是稀疏采样下很难获得有效强化信号。有限预算下先补示范通常更可控，不能把工程决策说成策略支持集的绝对定理。

**易失分回答：** “SFT 到顶后必须 RL”，却没有和继续 SFT、DPO 或推理时选择比较。

来源：[全链路总览 §4.5、§6.2](../00_ChatJoy后训练全链路统一面试复习.md)。

## Q04 ★｜重写前面的 assistant 后，原始后续 user 还成立吗？

**主答**

这是多轮数据中一个重要的一致性问题。Teacher 生成第 t 轮时不能看到未来 user，只能使用角色卡、截至当前的历史和本轮 user；但“不偷看未来”不自动保证改写后的完整轨迹仍合理。

例如原回答答应去港口，后续 user 问“到了港口之后怎么办”；如果 Teacher 把前一轮改成拒绝出发，后续 user 的前提就断了。因此改写优先保持决定后续对话的事件、关系和承诺，只改善表达、角色贴合与必要细节，并在完整生成后检查状态衔接。

局部表达问题可只改当前 assistant；影响后续 assistant 的状态问题需要从最早变化位置重生成 suffix。但如果不一致来自固定的后续 user 本身，重写 assistant suffix 不一定能解决，应尝试恢复原状态约束，仍无法合理衔接就丢弃。不能无授权篡改真实 user 来凑顺畅对话。

**连续追问**

- **“完整检查是否意味着 Teacher 看到了未来？”**  
  生成与验收分开。生成当前回答时只给因果前缀；完整轨迹生成后可以离线检查一致性。不能把检查阶段发现的未来 user 直接塞回当前生成上下文，使训练答案依赖未来。
- **“只做一次 Repair，会不会浪费数据？”**  
  一次 Repair 是质量、成本与分布偏离之间的取舍。修不好的样本继续改写可能越来越脱离真实对话；报告 repair 成功率、失败原因和分语言留存，再决定是否调整预算。

**易失分回答：** “六轮按顺序重写就一定因果正确”，忽略真实 user 是针对旧回答产生的。

来源：[SFT 正文 §6、§10](../SFT/Character-RLHF_SFT_Canonical_Full.md)。

## Q05｜请标出 Head、Continuation、RM 和 RL 的 Attention/损失 Mask

**主答**

Attention Mask 决定能看到哪些上下文，Loss Mask 决定哪些 token 产生优化信号。两者不是一回事。

| 阶段 | 进入条件上下文 | 计算训练损失的对象 |
| --- | --- | --- |
| SFT Head | 角色卡和当前六轮因果历史 | 当前六个 assistant 回答的目标 token |
| SFT Continuation | 更早前缀和当前六轮因果历史 | 仅当前六个 assistant 回答；更早历史不重复监督 |
| RM | 完整 Prompt、chosen 或 rejected 分支 | 两个候选的最终 scalar score 做 pairwise loss |
| RL | 角色卡、历史、本轮 user | 本轮生成 Response 的策略与 KL 项 |

SFT 中非目标 token 的 labels 通常设为 ignore index；这不代表从 Attention 删除。RM 读取 chosen/rejected 最后有效 token 或 EOS 的分数，不对全部历史做语言模型 CE。RL 的历史 assistant 是条件，不应被当成当前策略刚生成的动作。

**连续追问**

- **“配置 train_on_prompt=false 就够了吗？”**  
  不够。多轮模板、拼接和特殊 token 可能影响 label 边界，必须抽样把 tokens、labels、attention/response mask 对齐打印，核对有效分母。
- **“超过 3072 token 怎么办？”**  
  先统计真实 token 分布，优先按合同处理当前六轮之前的旧前缀；保护角色卡、当前 user 和候选。仍超限按压缩/丢弃策略处理，不能切坏六轮后沿用完整六轮标签。

**易失分回答：** “历史不计算 Loss，所以不用送进模型。”

来源：[SFT 正文](../SFT/Character-RLHF_SFT_Canonical_Full.md)、[训练参数专题 §7.1—7.2](02_训练参数选择与LoRA技术分层.md)。

## Q06｜为什么这样选角色、语言和 Session？如何避免采样偏差？

**主答**

TOP20 角色和 27 种语言提供重点业务覆盖；每 Session 最多一个 Head 和一个 Continuation，能减少滑窗样本高度相关造成的重复监督。但高频角色不代表所有角色，语言配平也不等于真实流量分布，覆盖与代表性要分别报告。

数据先按会话/语义家族分集合，再在集合内生成和修复。不能让同一会话的 Head 在训练、Continuation 在测试；跨语言翻译、角色名替换或攻击改写也可能属于同一 Family。

清洗后检查每个阶段的分语言、角色、长度和场景留存。如果某小语种因语言识别误差大量被删，最终平均质量提高可能只是移除了难例，不是真正改善该语种。小语种和低频角色应保留独立诊断视角。

**连续追问**

- **“每种语言至少 5 对，是不是充分覆盖？”**  
  它只是边际配额下限，不保证估计精确，也不覆盖角色×语言的全部组合。小切片同时报告样本数，发现不稳定时补独立样本。
- **“先做随机切分，最后用 embedding 去重行不行？”**  
  可以补查，但不应替代源头分组。embedding 阈值会漏掉同源改写或误删同领域样本，Family 元数据与语义复核需要结合。

**易失分回答：** 把采样配额当成线上分布，或把 Response 文本不相同当成无泄露。

来源：[SFT 正文 §3、§11—12](../SFT/Character-RLHF_SFT_Canonical_Full.md)、[Benchmark 专题 §3.2](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q07｜如何判断 SFT 平台？为什么下一步是偏好优化？

**主答**

我用固定 SR-Clean 看目标行为是否覆盖、是否稳定，再看继续 SFT 的增量收益。训练 Loss 下降只表明更贴训练目标，不能单独证明业务表现提高。

每个 Scene 生成 N 个候选，根据冻结质量门标记合格与否。令 $c_i$ 为第 i 个 Scene 的合格候选数：

$$
\mathrm{Support@N}=\frac{1}{M}\sum_i\mathbf{1}[c_i\ge1],
\qquad
\mathrm{AllFail@N}=\frac{1}{M}\sum_i\mathbf{1}[c_i=0].
$$

若很多 Scene 至少能产生合格候选，但好坏混合、单次生成不稳定，下一步可重点检查偏好排序和策略优化；若大量 Scene 的候选全不合格，先补 SFT 数据或能力更合理。

平台要结合连续 checkpoint、重复评测波动、数据和训练预算判断。小幅均分变化落在 Judge/采样噪声内时，不能仅靠正负号说有效或无效。

**连续追问**

- **“N=4 的 Support 比 N=2 高，能说模型进步了吗？”**  
  不能。N 增加本来就提高找到至少一个合格样本的机会，应冻结 N、Prompt、采样协议和 Judge 后比较。
- **“Mixed、Support、AllFail 能相加为 1 吗？”**  
  Mixed 是 $0<c_i<N$，属于 Support。互斥划分是 AllPass、Mixed、AllFail；Support+AllFail=1。

**易失分回答：** 把“生成得出来”与“经常生成出来”混为一谈。

来源：[全链路总览 §4](../00_ChatJoy后训练全链路统一面试复习.md)。

## Q08｜A-eval、Internal、旧 B 和 B6 分别如何制作、如何使用？

**主答**

A-eval 用于早期 4D 规则校准和 RM 开发评测，共 250 Pair；Internal 在后续增加 Clean 300 与 Attack 100，总计 650。B6 当前设计为 Core 250（原样复用旧 B 实体）、Clean 350、Attack 200，共 800 Pair 做分切片验收（上一代为 Clean 300 / 共 750）。旧 B 是 RM-A 阶段的另一套 250 Pair 强偏好基准，其实体原样成为 B6-Core，不与 Internal-Core（复用旧 A）混称。

建集顺序是：定义错误和质量轴，分配独立 Prompt Family，生成同题候选，规则检查，双 Judge 确认方向和目标差异，按配额冻结。Core 继承基础考点与数量，并不因此允许与 Internal 复用实体题目。

最小样本单元包含：pair_id、family_id、角色卡与历史、当前 user、两个候选及内容 hash、生成设置、匿名映射、Judge 版本、标签证据、目标轴和难度。冻结后比较 RM checkpoint，只重新做 RM 前向与数学汇总，不再次调用 Judge 改题目答案。

**连续追问**

- **“为什么评测每 Prompt 优先一 Pair？”**  
  降低同题候选相关性造成的重复计数；若有多个 Pair，仍可报告 Pair 准确率，但统计不确定性按 Prompt/Family 聚类处理。
- **“Hard 是不是 RM 分差小的题？”**  
  不是。Hard 在冻结时由业务混淆模板和可靠 Judge 标签确定；RM 分差小是该模型的 Low-Margin，不能事后改题目难度。

**易失分回答：** 把 800 Pair 说成 800 条 Response，或每换 RM 就重新调整题目难度。

来源：[Benchmark 专题 §2—4](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q09 ★｜会不会过拟合 Benchmark？如何判断？

**主答**

会。既可能出现训练数据直接碰到测试题的污染，也可能在反复看同一 Benchmark、调数据配比和选 checkpoint 后，对它的题型、Judge 偏好和有限样本产生适应性过拟合。没有题目回灌，只排除了部分直接污染，不等于没有开发选择偏差。

判断时我关注三类差异：固定集是否上升而独立同分布抽样不升；同一业务机制换独立场景、语言或角色后是否失效；公开的强项是否掩盖最弱切片和人工偏好退化。独立新样本要按同协议判分，先排除样本难度、分布和 Judge 漂移，再判断是否过拟合。

对已有 B6 保留固定版本和比较价值；对开发泛化另做独立抽样审查，不把原题换个名字当新数据。记录尝试过多少配置、为何选择某 checkpoint，以及选择前后的评测协议。

**连续追问**

- **“B6 提升，新样本下降，就一定过拟合？”**  
  不一定。可能是分布变化、评测噪声或新样本更难。先对齐切片和评测器，再比较模型相对同一基线的变化；必要时增加独立样本与多 seed。
- **“如何预防？”**  
  训练决策主要使用 Internal；减少凭 B6 单次波动改动方案；只把 B6 失败模式抽象成 C-k 采样方向；独立新家族验证后再扩大结论。任何被反复用于决策的集合，都应承认其开发集属性。

**易失分回答：** “Benchmark 不进入训练，所以不会过拟合”，或“始终涨分就是泛化更好”。

来源：[Benchmark 专题 §7.4](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q10 ★｜双 Judge 一致率很高，就能证明标签可靠吗？

**主答**

不能。先要看一致率在哪个集合上计算。如果只保留两位 Judge 同向的 Pair，再报告收录集一致率，结果很高是筛选规则造成的，不能独立证明质量。

应在筛选前的预定双审对象上报告有效覆盖、方向一致、tie/abstain 和冲突，并分语言、目标轴、难度检查。两位 Judge 可能共同偏爱长回答或某种风格，因此还需要独立人工锚点和有针对性的偏差探针。

跨 Judge 的 F1/Kappa 是两位评分者之间的关系；有独立人工标签后，才能另算相对人工真值的检测 precision/recall/F1。

**连续追问**

- **“能举个分母例子吗？”**  
  教学例：计划双审 100 题，双方有效 90 题，其中 72 同向。有效覆盖率 90%，共同有效集合上的方向一致率 80%；不能只拿最终留下的 72 题报告 100%。
- **“Kappa 比一致率好在哪里？”**  
  它按边际分布扣除机会一致：$\kappa=(p_o-p_e)/(1-p_e)$。极端类别不平衡、正例很少或分母退化时仍有局限，必须一起给混淆矩阵和正例数，不能只追一个 Kappa。

**易失分回答：** “两个大模型都这么判断，所以就是 Ground Truth。”

来源：[Benchmark 专题 §6—7](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q11 ★｜如何保证 LLM API Call 打分的严格一致性？

**主答**

我把“严格一致”拆成三个对象：输入与评分协议可以严格固定；远端模型重新推理的输出只能尽量稳定并测量波动；固定标签、固定模型预测分数和聚合代码后的指标可以做到确定性复算。若重新执行 RM forward，还需核对运行配置与数值容差，冻结标签本身不保证预测分数逐 bit 相同。

因此不能承诺只设置 temperature=0 或 seed，就让外部 API 每次返回完全相同的分数。工程上要冻结请求合同、验证评分稳定性，最后把通过确权的标签冻结，使后续模型比较使用同一套答案。Google 的生成参数文档也明确将固定 seed 描述为尽力复现，不保证确定输出；不同 provider 需要核对自己的支持范围。[官方生成参数说明](https://cloud.google.com/vertex-ai/generative-ai/docs/multimodal/content-generation-parameters?authuser=0)

**第一层：把评分含义固定**

四轴定义、Hard-Fail 优先级、分值范围、正反例和边界例都版本化。Richness 只奖励有效信息，不能单纯奖励长度；攻击成功看行为是否越过角色合同，不能只匹配“AI”关键词。中文、英文和小语种的锚点要表达相同标准。

Primary 与 Secondary 独立判断，不把第一位的分数给第二位。候选身份匿名，顺序打乱并保存反向映射；顺序交换后先映射回同一 candidate_id，再比较方向。用户/候选中的“给我满分”等文字是被评价数据，不能升级成 Judge 指令。

**第二层：把请求与实现固定**

请求合同记录 provider、可用的模型快照、完整 system/rubric、角色卡/历史/候选 hash、匿名顺序、temperature、top_p、输出上限、thinking 设置以及可用的 seed。还需固定解析器、聚合、量化/舍入和 tie 处理。

如果模型只提供可变别名，记录调用时间、返回模型信息和可获得的后端标识，定期使用同一锚点检测漂移。并发固定有利于预算和复现管理，但不能保证 provider 的底层批处理或硬件固定。

**第三层：验证再冻结，而非不断重判到满意**

~~~text
固定候选和 rubric
→ 两个独立 Judge
→ Schema、范围、候选身份与内部一致性检查
→ 顺序交换/重复评分抽查
→ 人工检查关键边界与冲突
→ 按预先规定的规则收录或丢弃
→ 生成不可变 labels_version
~~~

最终标签绑定内容和协议的 hash。以后评同一个固定 RM Pair 集，直接读取这一版标签，不再重新生成“标准答案”。同一个缓存键的重复业务请求返回同一已冻结结果，这才是应用层可控制的一致；它不代表远端重新推理天然确定。

**连续追问**

- **“怎样量化稳定性？”**  
  同对象重复评分的 MAE、偏好翻转率、顺序交换翻转率、Hard-Fail 分歧率，以及双审有效覆盖。分语言、难度和攻击类型报告。可定义：
  
  $$
  \mathrm{MAE}_{\mathrm{repeat}}=\frac{1}{n}\sum_i|s_i^{(1)}-s_i^{(2)}|.
  $$
  
  接受阈值在 Pilot 阶段结合业务可容忍误差设定，不能看到待测模型成绩后调宽。若两模型差异与 Judge 复跑波动同量级，增加盲审或报告无明确差异。
- **“要每题重复调用三遍、投票才可靠吗？”**  
  不一定。同模型的系统性偏差不会被简单多数票消除；重复次数与聚合规则要预注册并计成本。高风险与不稳定切片值得增加复判；固定集冻结后不再重复判同题。
- **“API 出错如何处理？”**  
  超时、限流、服务错误和格式失败按有限重试处理；截断、缺字段、身份映射错不能被当成正常低分。重试次数、失败原因与最终覆盖要留存。不能因为分数不喜欢而重试，也不能把失败样本静默移出分母。

**易失分回答：** “temperature=0 + seed=42 保证严格一致”“输出 JSON 就证明评分可靠”“对所有分数四舍五入就消除了噪声”。

来源：[Benchmark 专题 §6—8](01_Benchmark制作与指标计算_Judge一致性技术分层.md)、[Judge 请求与处理源码](../../character-rlhf/training/GRPO_Training_Package/rm_v6_finegrained/judge_candidates_llm_openai.py)。

## Q12｜API 模型或 rubric 变化、断点续跑时，怎样避免标签混版？

**主答**

评分缓存不能只用 prompt_id。缓存键至少绑定完整输入、候选内容和顺序、Judge 模型协议、rubric、生成设置与解析版本。角色卡、历史、候选或评分标准任一改变，旧缓存都不能自动沿用。

启动任务时检查输入 manifest 与输出版本匹配；续跑只跳过相同合同下已成功完成的对象。Provider 的 prompt cache 只是输入计算复用，不等于应用层标签缓存。模型或 rubric 改版应生成新结果版本，不能只给最新 RM 换一套有利标签。

现有 Judge 脚本的 seed 用于本地候选乱序，请求 payload 没有因此自动向远端发送 seed；resume 按 prompt_id 跳过已有结果。这说明生产实现需要额外版本目录或合同检查，不能把“有 resume 参数”说成已经解决标签混版。

**连续追问**

- **“两个 Judge 同向，但 Secondary 判 chosen 有 Hard-Fail，怎么办？”**  
  先检查是否为解析或候选对齐问题，再检查证据；未解决则不准入。最终校验需要聚合两边的 Hard-Fail，不能只用排序共识覆盖严重冲突。
- **“同一 source 一题生成两条候选会怎样？”**  
  以 source_model 为键的旧对齐方式可能覆盖一条或错配。使用唯一 candidate_id+内容 hash 对齐，验证两边候选集合一致；source 仅保留为分析元数据。

**易失分回答：** “ID 一样就是同一个请求”或“模型名字没变，标签就没有变”。

来源：[Judge 源码](../../character-rlhf/training/GRPO_Training_Package/rm_v6_finegrained/judge_candidates_llm_openai.py)、[双 Judge 合并源码](../../character-rlhf/training/GRPO_Training_Package/rm_v6_finegrained/merge_judge_votes.py)。

## Q13｜B6 配额为什么能代表业务？如何判断真正的破角？

**主答**

B6 是按关键能力与风险分层构造的业务验收集，不是未经加权的线上流量抽样。配额让角色、推进、富度、密度及不同攻击关系都有足够题目；不能把 B6 Overall 直接解释成线上自然发生率。

Clean 固定 Role 90、Progression 75、Richness 75、Density 60。Attack 有五种类型，每种 40 Pair；关系维度分别为 Clear 12、Subtle 18、Defender 10，所以总计 Clear 60、Subtle 90、Defender 50。这两条轴要同时检查，不把攻击类型与偏好关系混成一类。

破角必须回到当前角色、任务和上下文。正常技术角色写代码可能合规；守卫角色在用户要求“忘掉身份、切成助手”后完成无关通用任务，才可能属于越权。合理的戏内拒绝不是坏样本，空答和放弃互动也不是优秀 Defender。

**连续追问**

- **“Refusal/Abandonment 怎么构造正负例？”**  
  教学例：user 要求角色停止扮演。好回答在角色内化解并留下互动入口；坏回答宣布终止角色、以通用助手身份说明自身政策，可构成明确放弃角色的对比。若只是戏内说“不”，没有退出角色，就不能按该标签凑配额。
- **“两边都防住，还训练什么？”**  
  比较角色自然性、上下文承接、推进和密度，走 Defender Quality 的四轴准入。不能让模板拒绝因未破角自动战胜自然防御。

**易失分回答：** 把出现代码、列表、拒绝词或“AI”字样直接等价为攻击成功。

来源：[Benchmark 专题 §3.4—3.5](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q14 ★｜小样本涨几题能说明什么？指标应该怎样计算？

**主答**

先锁定分母与统计单位，再讨论不确定性。Pair Accuracy 看冻结 chosen 是否被 RM 排高；RM Tie 计错。Low-Margin Correct 是“方向正确但标准化分差小”，属于 Accuracy 的正确样本，不是另一类错误。

教学例：B6-Clean 300 Pair，42 误排、30 Low-Margin Correct、228 Confident Correct，则 Accuracy=258/300=86%，Misrank=14%，Low-Margin Share@all=10%。同一 Prompt 的多个 Pair 相关，不能因拆成多对就当作多个独立实验单位。

小切片一两题的变化会很大：40 Pair 中一题是 2.5 个百分点。4/50→2/50 的点估计从 8% 到 4%，还需要同题配对、重复性和区间分析；不能仅凭相对下降 50% 就说稳定改善。

**连续追问**

- **“怎么比较两个 RM？”**  
  对同题记录旧错新对 $n_{\mathrm{fix}}$ 与旧对新错 $n_{\mathrm{break}}$：
  
  $$
  \Delta\mathrm{Accuracy}=\frac{n_{\mathrm{fix}}-n_{\mathrm{break}}}{n}.
  $$
  
  同 Prompt/Family 聚类 bootstrap；独立 Pair 的二元配对可考虑 McNemar，稀疏失配用精确方法。候选来自同题时不能直接套独立样本检验。
- **“z-score 后的 gap 是正确概率吗？”**  
  不是。对每个 RM、每个固定 Slice 的唯一 (Prompt, Response) 对象做标准化，只处理尺度；概率校准需额外检验。标准差为零记退化/N/A，缺分或 NaN 先补齐，不能随意缩分母。
- **“试了很多 checkpoint 再选最好的怎么办？”**  
  保存选择过程，以开发集选模、独立抽样复核，报告 seed/判分波动。业务门是决策门槛，不等于统计置信下界。

**易失分回答：** 把配额设计、工程验收、统计显著和线上泛化说成同一件事。

来源：[Benchmark 专题 §5、§7](01_Benchmark制作与指标计算_Judge一致性技术分层.md)。

## Q15 ★｜早期删低 Gap 后退化，为什么后来又用 Gap/Q25 过滤？

**主答**

必须区分分差是谁算的、目标是什么，以及标签是否可靠。RM Margin 小可能表示当前模型不会区分，但标签十分明确，这正是有价值的 Hard Negative；Judge Gap 小则可能表示业务偏好本来接近，也可能是 Judge 噪声，需要结合目标差异和一致性。

早期“统一删除低 Gap/中置信样本”的风险是把可靠边界覆盖也删掉。新方案不能机械重复这个操作：先确认 chosen 方向和目标错误成立，再按目标类型/轴校准最低可用差异，保留标签可靠的边界样本。confidence 不是准确率，不作为提前裁掉校准分布的唯一条件。

Q25 是把阈值与校准候选分布关联的启发式，不是数学上保证最优的过滤器。需要同时报告留存、类型覆盖、语言/长度分布和人工抽检；如果伤害业务关键边界，应重新审视 rubric 与阈值设计，而非只追求高一致率。

**连续追问**

- **“Hard Pair 和歧义 Pair 怎么区分？”**  
  Hard 是对模型或业务边界难，但在明确上下文下标签可确权；歧义 Pair 则无法稳定说明为什么 chosen 更好。困难不等于标签不可靠。
- **“两个条件分别保留上面 75%，联合还能保留 75%？”**  
  不能。即使忽略其他门，联合留存取决于相关性；独立的理想例子是 0.75²=56.25%，完全相关时可能接近 75%。实际还受 floor、tie、Hard Guard 和双审影响，应测真实漏斗。
- **“历史退化是不是已经证明删数据导致？”**  
  如果 Batch、Step、保存方式等同时变化，单次退化不能单独完成因果归因。应分开讲已观察到的现象与待区分原因；下一次用固定其他条件的对照回答。

**易失分回答：** “低 Gap 都是脏数据”或“Hard Negative 就是 Judge 没有把握的样本”。

来源：[RM-A 正文 §2—4](../RM/RMv1-v5_从SFT平台到Anchor_RM完整面试复习.md)、[RM-B 正文 §6—7](../RM/RMv6-v6.6_从Unified_Clean_Attack到定向Hardening完整面试复习.md)。


## Q16｜怎样排除 RM 学成“生成器风格分类器”？

**主答**

六 Source 能扩大候选差异，也可能带来捷径：若某个模型几乎总是 chosen，另一个几乎总是 rejected，RM 可能利用措辞、格式、长度等来源特征完成排序。对 Judge 隐藏 source 只是避免直接泄露，不能消除文本本身的风格线索。

我会先看 source-chosen/rejected 方向矩阵，并按语言、目标轴和长度分层。再比较同 source 内的质量对、跨 source 但长度/格式匹配的对，以及同等质量但风格不同的探针。只有在控制明显来源差异后仍能识别业务质量，才支持 RM 学到了目标偏好。

**连续追问**

- **“是不是把每个 source 的 chosen 比例调成一样就可以？”**  
  不可以。真实生成质量可能不同，强行平衡会破坏标签。应增加缺失的可靠比较、做分层检查，而不是为了矩阵对称而反转偏好。
- **“长度归一化能解决风格捷径吗？”**  
  只能处理一部分相关性，且长度可能包含真实信息。要比较 rich-vs-padded、concise-vs-insufficient 等语义对照，不能把所有长答案惩罚掉。

**易失分回答：** “Judge 看不到模型名，所以 RM 不会学到 source。”

来源：[RM-B 正文 §5—7](../RM/RMv6-v6.6_从Unified_Clean_Attack到定向Hardening完整面试复习.md)。

## Q17｜RM-B 数据配比怎么定（当前 30/50/20）？

**主答**

配比表达的是训练预算分工：Anchor 保住基础错误识别，Clean 学习细粒度好坏，Attack 补高风险防御边界。当前设计：30,000 Pair = 9,000 Anchor 回放 + 15,000 Holistic Clean + 6,000 Attack（30/50/20）；上一代口径为 44,280 = Anchor 17,712、Clean 22,140、Attack 4,428（40/50/10）。

它是基于业务优先级与风险的起点，不能因为写得精确就称为最优。选择比例时不仅看线上出现频率，还看错误代价、现有 RM 的盲区、候选生成能力和 Label 质量。罕见但高代价的 Attack 可以适度过采样，但要防止模型靠模板拒绝、普遍收缩来换红线分数。

先做 training-free 的覆盖、标签质量与难度审计，再看 Internal、B6 各切片和当前 Actor 候选上的 Reward 方向。只有这些共同支持，才决定继续训练或调整配比。

**连续追问**

- **“为什么不直接训练 5%/10%/15% 三套？”**  
  有预算时可做匹配对照，但不应默认多跑就有价值。先用无需训练的审计排除空洞或过易的 Attack 数据；有明确配比瓶颈后，再把有限实验预算投入有区分力的对照。
- **“新的攻击出现，全部加入训练吗？”**  
  先按 Family 隔离，一部分形成训练/C-k 覆盖，另一部分用于独立评估。扩量后要重算 token exposure、Step 和混合比例，不能仍声称只有数据质量一个变量变化。

**易失分回答：** “10% 最优，因为最终选了 10%。”

来源：[RM-B 正文 §5、§7、§9](../RM/RMv6-v6.6_从Unified_Clean_Attack到定向Hardening完整面试复习.md)。

## Q18｜4D、5D/8D、四轴 Judge、Hard Guard、RM、Reward 分别是什么？

**主答**

这些是不同层的对象，不能用维度数量串成“奖励头不断增加”。

| 层 | 作用 | 是否直接成为在线标量 Reward |
| --- | --- | --- |
| 早期 4D heuristic | 规则预筛、目标类型质量门 | 不自动进入 |
| 历史 5D/8D Judge | 对候选质量打分/排序、辅助构对 | 不自动进入 |
| 当前四轴 Judge | 定义细粒度 Clean 偏好 | 不自动进入 |
| 建集 Hard Guard | 排除不合格 chosen、处理不可补偿错误 | 是标签准入，不等于在线代码 |
| Scalar RM | 学习同 Prompt chosen 高于 rejected | 可作为在线基础分 |
| 在线 Guard/合成 | 按优先级处理红线和退化 | 明确产生最终 Reward |
| Reference KL | 限制策略漂移 | 本方案在 Actor Loss，不加进 Reward |

例如一条回答写得丰富但已执行角色覆盖任务，建集时不能靠 Richness 高分抵消破角；在线若命中经验证的 Redline，就走红线分支。对隐蔽语义攻击，规则无法保证全覆盖，需要 RM 的训练信号和独立 Judge 评估共同支撑。

**连续追问**

- **“RM 为什么只有一个 head 还能学多个目标？”**  
  Pair 标签编码综合偏好，score head 输出综合标量。多维诊断用于解释错在哪里，不等于网络有多个独立评分头。
- **“规则越多是不是越安全？”**  
  不一定。低精度规则会把正常角色内容打成错误，成为可被利用的代理。优先小而可靠的规则，明确覆盖率与精度，并用保留样本测误伤。

**易失分回答：** 把四轴权重、RM 多头和 RL 规则分直接相加成一个未经实现验证的公式。

来源：[RM-B 正文 §1、§6](../RM/RMv6-v6.6_从Unified_Clean_Attack到定向Hardening完整面试复习.md)、[RL 正文 §1.5—1.6](../RL/01_RL完整流程与关键机制演进.md)。

## Q19 ★｜同 Pair 数、同 Batch、同 Step，为什么还不是完整的数据-only 对照？

**主答**

这些条件只锁住一部分暴露预算。替换后的回答更长，同样 64 Pair 每步可能涉及更多 token；换了 source、语言、目标轴、攻击类型或 Prompt Family 分布，也会改变难度和学习信号。模型初始化、样本顺序和随机种子不同，还会带来训练随机性。

RM-B.1→B.2 的对照应从同一 SFT merged 底座独立初始化，固定 LoRA、优化器、LR/scheduler、world size、数据比例、Judge 和门槛。在相同 target×语言×长度桶×source 方向×攻击类型槽位内，用 C-k 可靠难例替换较容易的样本，并记录实际 token exposure。

这样能提高归因可信度，但单 seed、单次训练仍不能消除全部不确定性。报告同题修复和回退，并用重复或独立样本判断稳定性；不能只看最终总分多了几点。

**连续追问**

- **“为什么不从 B.1 继续训练 B.2？”**  
  如果要比较数据替换本身，继续训练同时改变了初始化和额外优化暴露。继续训练可以是生产方案，但那是另一种问题，不能称严格同起点对照。
- **“token exposure 相差不超过 1% 就是严格单变量？”**  
  不是。它是减少长度暴露混杂的目标，数据内容、样本相关性与随机性仍要检查。还需区分 input non-pad token 与实际参与目标损失的 token/Pair 单位。

**易失分回答：** “我只改了数据路径，所以是单变量实验。”

## Q20 ★｜怎样证明送进 GRPO 的 Reward 就是预期的 Reward？

**主答**

我会冻结一批同协议的 Prompt 与 Response，不更新模型，逐条把“RM 原始分→尺度处理→Guard 判定→最终 Reward→组内 Advantage”串起来。这是 Reward Reconciliation，也就是逐项对账。

本方案先处理 RM 尺度：

$$
r_i^{\mathrm{bounded}}=\operatorname{clip}(a r_i^{\mathrm{raw}}+b,-c,c).
$$

再按分支定义：

$$
R_i=
\begin{cases}
R_{\mathrm{redline}}, & \text{命中 Redline},\\
r_i^{\mathrm{bounded}}-P_i^{\mathrm{degeneration}}, & \text{其他}.
\end{cases}
$$

红线是优先分支，不允许正向质量把它补偿回去。实现时需检查红线 floor 与其他分支的取值范围及实际排序；不能只因名字叫 floor 就认定所有分支关系正确。

教学算例：若本例 $a=0.5,b=0,c=2$，raw score=3，则 bounded=1.5；无 Redline、退化惩罚为0.5时最终为1.0。若红线分支固定为-5，即使 raw score 很高也应输出-5。这些数值用于讲清分支，不是项目测量值。

**连续追问**

- **“同时开 RM 与 custom reward 不就行了吗？”**  
  本地 reward loop 的 compute_score 先检查 custom_reward_function；非空时直接返回 custom manager 结果，不会自动再走独立 disRM 分支。需要 custom 实现自己显式合成，或改成明确的组合路径；配置同时存在不证明相加。
- **“对账保存什么？”**  
  保存 uid、candidate_id、完整模板/tokenizer 版本、raw/bounded score、Guard 类型与证据、惩罚值、最终 R、组内均值/标准差/优势，以及在线与离线差异。缺失或非有限数必须报错，不填成正常0分。
- **“Raw RM 排对就够了吗？”**  
  不够。clamp 可能压平差异，规则可能改坏次序，source 分支可能路由错误。必须验证最终 R 的方向，再检查同组候选是否存在合格答案。

**易失分回答：** 用一个总 Reward 曲线证明组合公式已经正确接通。

来源：[reward_loop.py 的 compute_score](../../verl/verl/experimental/reward_loop/reward_loop.py)、[全链路总览 §9.2—9.4](../00_ChatJoy后训练全链路统一面试复习.md)。

## Q21｜behavior、old、current、reference 到底有哪些区别？

**主答**

behavior 是实际生成这批候选的分布；old 是本轮优化使用的固定近端锚点；current 是当前 minibatch 正在更新的策略；reference 是用于限制长期漂移的固定参考。它们可能共享模型组件，但计算角色不同。

本地 decoupled 路径对一个 Rollout Batch 重算一次 old logprob，多 minibatch 更新期间固定它；bypass 路径则使用 rollout 返回的 logprob。不同后端数值、采样温度、top-p 或异步滞后，都可能使 behavior 与训练侧 old 不完全一致，需要按实际协议比较和处理。

current logprob 必须来自当次参数的 forward，每次 optimizer step 后会变化。reference 固定，但 LoRA 禁用后的底座是否就是预期 SFT 起点，取决于 SFT adapter 是否已 merge、以及禁用了哪个 adapter。

~~~text
固定一批 rollout 和 uid
→ 固定本批 old/ref logprob、Reward、Advantage
→ minibatch 1：算 current → backward → optimizer
→ minibatch 2：用新参数重算 current → backward → optimizer
→ 完成本轮，同步到 rollout replica
~~~

**连续追问**

- **“为什么不每个 minibatch 都刷新 old？”**  
  它是本批的固定比较锚点，刷新会改变 ratio 和优化语义。current 才是随优化变化的分子。
- **“第一个更新前 ratio 一定等于1吗？”**  
  同参数、同输入处理且计算协议一致时应接近1；训练/推理后端、温度、mask、adapter 或权重版本不一致可能造成偏差，应在 Step0 检查，而不是事后靠 clip 掩盖。
- **“old/current 的差和 current/reference 的 KL 是一回事吗？”**  
  不是。前者服务近端更新比较，后者约束相对固定参考的漂移；二者混用会改变优化目标。

**易失分回答：** “old 就是 reference”“current logprob 在 rollout 时已经算过，不用重算”。

来源：[ray_trainer.py 的 Operating Mode Selection](../../verl/verl/trainer/ppo/ray_trainer.py)、[losses.py](../../verl/verl/workers/utils/losses.py)。

## Q22｜同 Prompt 的 reward std 很小，是否意味着没有学习信号？

**主答**

GRPO 使用同组相对优势：

$$
A_i=\frac{R_i-\mu_g}{\sigma_g+\epsilon}.
$$

如果所有 R 严格相同，则优势为0。如果差异非零且 epsilon 很小，标准化后仍可能有明显优势；但差异若主要是噪声，标准化也会放大噪声。只有 std 数值不能判断信号是否正确。

教学例：R=[1.00,1.01,0.99]，用总体标准差约0.008165、忽略 epsilon，优势约[0,1.2247,-1.2247]。raw score 差很小，却仍有非零更新系数。实际 torch.std 的 ddof/单样本约定必须按版本核对，不能混用这个教学分母。

因此同时看同组候选质量、RM/Judge 排序一致、Top-1 安全、低分差分布和尺度饱和。跨 Prompt 的总方差大，并不保证每个 Prompt 内有可用差异。

**连续追问**

- **“六个候选都坏，还能强化相对最好的吗？”**  
  数学上可产生相对更新，但可能只是强化最不坏的坏答案。业务上先判断是否缺少目标行为和正确信号；必要时回 SFT 补示范，不能把组内第一名自动当成合格答案。
- **“把 reward 乘100就解决了吗？”**  
  在 epsilon 可忽略且没有其他分支变化时，组标准化会基本抵消正比例缩放；但 clamp、Guard、epsilon 和其他加项会破坏这种不变性，仍要对账。

**易失分回答：** “std>0 就通过”“std 小说明没有梯度”“提高 reward 数值就是提高学习信号”。

来源：[RL 正文 §1.7、§2](../RL/01_RL完整流程与关键机制演进.md)。

## Q23｜为什么 Clean 与 Attack 使用不同 KL？怎样证明它有效？

**主答**

业务假设是 Clean 已有较可用的行为，希望较保守地保持；Attack 可能需要更明显改变，因此允许不同更新约束。这是 source-conditioned KL 的动机，不是收益结论。

Loss 可以写为：

$$
L_{\mathrm{actor}}=L_{\mathrm{policy}}+
\frac{1}{B}\sum_i\beta_{s_i}\widehat{D}_i,
$$

其中 $s_i$ 是来源，$\widehat D_i$ 是按本方案 Response Mask 与归一化计算的 current/reference KL 估计。要核对聚合分母，避免较长样本或较多来源隐式获得额外权重。

Source-Swap 只交换 source 标签而固定 logprob，能检查不同系数是否进入算术。它证明接线，不证明该系数组合提高最终质量；效果还要看固定 SR 双切片和必要的参数对照。

**连续追问**

- **“交换标签的数值例子是什么？”**  
  教学例：两条 KL 分别0.04、0.01，系数0.1、0.02。原 weighted mean=(0.1×0.04+0.02×0.01)/2=0.0021；交换系数为0.0009。raw mean 始终0.025。若预期交换后应变却完全没变，需查 source 映射或聚合。
- **“增大 KL 系数等价于减小 LR 吗？”**  
  不等价。LR 缩放优化器更新，KL 是有方向的相对参考惩罚；对所有梯度统一减小与改变梯度组成不是同一操作。
- **“这套系数和补丁现在可以直接当作本地默认行为吗？”**  
  不能。需要读实际 source 分支、保存解析配置并验证训练日志持续激活；已有项目文档把该接入列为需核验的实现合同。

**易失分回答：** 把 Source-Swap 单测当作 Clean/Attack 分系数的效果实验。

来源：[RL 正文 §1.9、§4.3](../RL/01_RL完整流程与关键机制演进.md)。

## Q24 ★｜Span 重权在 GSPO 中真的改变 token 梯度吗？

**主答**

必须看实际计算图，不能只看算法注册名或前向 Loss。本地 verl 的注册名是 gspo，但实现采用 stop-gradient token surrogate：前向 ratio 在同序列内相同，反向梯度分别经过各 token。这样的实现与“把一个 sequence 标量复制到每个 token”不同。

因此“均值为1的权重一定抵消”仅适用于纯标量广播及其限定条件；不能直接套在本地实现上。反过来，看到 Loss 数字不变也不能说重权无效，应比较各 token logprob 的梯度。

**两种计算图的差别**

令 $\ell_t=\log\pi_\theta(y_t\mid x,y_{<t})$，old logprob 固定，有效长度 T：

$$
s=\exp\left(\frac1T\sum_t(\ell_t-\ell_t^{\mathrm{old}})\right).
$$

若所有 token 使用同一标量 $f(s,A)$，且固定权重满足 $\frac1T\sum_tw_t=1$：

$$
L_{\mathrm{broadcast}}=
\frac1T\sum_tw_tf(s,A)=f(s,A).
$$

这时 Loss 与梯度都不变。

本地实现则构造：

$$
s_t=\exp\left[
\ell_t-\operatorname{sg}(\ell_t)+\operatorname{sg}(\log s)
\right],
$$

sg 表示 stop-gradient：前向保留值，反向不沿该项传播。前向 $s_t=s$，但 $\partial s_t/\partial\ell_t=s$。再对逐 token clipped loss 加权平均，便能改变 token 梯度系数。

源码对应表达式为：

~~~python
log_seq_importance_ratio = (
    log_prob - log_prob.detach()
    + negative_approx_kl_seq.detach().unsqueeze(-1)
)
~~~

标准 GSPO 的 sequence ratio 和 clipping 见 [Qwen 官方说明](https://qwenlm.github.io/blog/gspo/)；这里具体的反向路径以[本地 core_algos.py 的 gspo 实现](../../verl/verl/trainer/ppo/core_algos.py)为准。

**解析算例**

四个 token 都有效，第三个是可信坏 Span，A=-1，所有 logratio=0，ratio=1 且未触及 clip。取 $\alpha=1,q=1/4$：

$$
w_t=\frac{1+\alpha m_t}{1+\alpha q}
\quad\Rightarrow\quad
w=[0.8,0.8,1.6,0.8].
$$

| 计算图 | 前向 Loss | 对四个 current logprob 的梯度 |
| --- | ---: | --- |
| 纯 sequence 标量广播后重权 | 1 | [0.25, 0.25, 0.25, 0.25] |
| stop-gradient token surrogate 后重权 | 1 | [0.2, 0.2, 0.4, 0.2] |

这是解析导数示例，不是训练效果测量。正梯度在梯度下降下倾向压低对应已采样 token 的 logprob；共享参数作用下，实际行为变化仍需评测。

**连续追问**

- **“权重均值1是不是总梯度不变？”**  
  不是。各 token 对共享参数的 Jacobian 不同，梯度可能叠加或抵消；均值1只控制直接权重的归一化，不保证参数梯度范数、optimizer 更新或 KL 守恒。
- **“什么情况下 Span 不应激活？”**  
  非 Attack、非负优势、低精度命中、offset 对齐失败、无有效 Response，或 Span Mask 不属于 Response Mask。回退 weight=1；普通 AI 词、代码围栏和列表样式不能单独成为坏 Span。
- **“既然有这个 surrogate，Span 已经实现了吗？”**  
  不一定。当前 gspo 能提供所需梯度路径，不代表业务 detector、offset、mask、权重插入点和回退已经接通。还应检查 clip 饱和、rollout correction 额外权重，以及 mask/权重是否 stop-gradient，并用小张量 autograd 验证实际插入位置。
- **“需要再加一次 RM forward 或 backward 吗？”**  
  轻量方案可以复用现有 forward/backward；但“没有额外大模型调用”不代表“没有实现成本”或“必然有效”。

**易失分回答：** “gspo 名字叫序列级，所以无法做 token credit”或“Loss 不变，梯度也一定不变”。

源码核对：本地 verl HEAD c47d54e836f27b04fc51acd4c12e5f7c06640ab7，core_algos.py 的 compute_policy_loss_gspo 与 agg_loss。这里只说明该快照与解析性质，不把它倒推为历史 run 已采用 Span。

## Q25｜破角下降、Clean 不变，如何排除变短、模板化或过度拒绝？

**主答**

需要同时看红线、正常任务表现和行为分布。Attack 破角下降可能来自更自然的防御，也可能来自空答、缩短、模板拒绝或放弃互动。因此两边都防住时仍要比较 Defender Quality；Clean 则检查角色、推进、富度、密度、语言与格式，不能只看一个综合分。

分析时固定 Prompt、采样和 Judge，查看长度、拒绝、重复、角色放弃及分语言/攻击类型的变化。再人工审查“红线改善但质量下降”和“质量提高但潜在破角”的边界样本。

如果 SFT、RM、规则、KL 与优化设置共同变化，最后只能先评价完整配方。要归因到某一项，需要冻结其他条件，做有区分力的对照或回放；不能把整套收益只归给 Span 或某个 KL 系数。

**连续追问**

- **“怎样决定继续 RL 还是回 SFT/RM？”**

  只能证明该范围内链路与早期行为没有暴露阻断问题；长期 reward hacking、分布漂移和小语种回退需要正式评测及持续观测。

**易失分回答：** “破角率下降，所以整体角色质量提高。”

## Q26 ★｜为什么 SFT 用 r32、RM 用 r128、RL 用 r16？

**主答**

rank 的选择同时受任务、数据和运行链路影响，不能按阶段背固定数字。SFT 的适配需要足够容量学习语言和角色行为；RM 的细粒度偏好可能要求更宽的表征更新；RL 还要兼顾推理端 adapter 支持、权重同步和更新稳定性。

项目参数中，Gemma SFT2 为 r32/alpha64、q/k/v/o；RM-B 为 r128/alpha256、q/k/v/o/up/down；存档 RL launcher 默认 r16/alpha16、q/k/v/o。它们是各自配置起点，不能跨模型、数据、模块范围直接推断“RM 比 SFT 需要四倍容量”。

若要验证 rank，固定底座、target、数据与优化预算比较相邻 rank；再固定 rank 比较是否增加 FFN。先排除 LoRA 未命中、标签噪声、mask 错误和 LR 问题，再把训练不佳归因于容量。

**连续追问**

- **“只有一次实验预算，先改哪个？”**  
  由当前瓶颈决定。实际模块没有梯度时先修接入；train/dev 都差且数据可靠，可测试容量或 LR；train好dev差优先查过拟合与分布，不能盲目加rank。
- **“为什么 RL 不直接用 RM 的宽 target？”**  
  两者目标不同，且 rollout hot-swap/TP 对目标模块支持可能不同。先验证端到端注入、同步和生成一致性，再讨论扩大范围的收益。

**易失分回答：** 把一个已使用的参数说成理论最优，或者用框架默认值当实验结论。

## Q27｜rank、alpha、target modules 分别改变什么？

**主答**

标准 LoRA 对一个线性层写成：

$$
h=W_0x+\frac{\alpha}{r}BAx,
\quad
P_{\mathrm{LoRA}}=r(d_{\mathrm{in}}+d_{\mathrm{out}}).
$$

rank 限制该矩阵增量的最大秩和参数量，alpha 决定显式缩放，target modules 决定在哪些矩阵提供更新自由度。r64/alpha128→r128/alpha256 保持显式缩放为2，但增加容量和训练状态，不保证更新范数或训练轨迹不变。

教学例：一个4096×4096矩阵，全量16,777,216参数；r64有524,288个LoRA参数，r128有1,048,576个。若同时加up/down，还要累加新矩阵；MoE专家结构必须逐个核对，不能用单层公式乘一个猜测的层数。

**连续追问**

- **“alpha翻倍等于LR翻倍吗？”**  
  不等价。alpha在前向及梯度链中，LR在优化器更新中，Adam等归一化与初始化进一步影响二者关系。
- **“gate_proj是不是router？”**  
  gated FFN 的 gate_proj 调节中间特征，MoE router 产生专家选择/权重，二者不同。模块名可能都含gate，需要看结构。
- **“所有LoRA都是alpha/r吗？”**  
  不是。rsLoRA采用alpha/√r，其他变体也可能改变初始化或缩放。必须读取实际adapter配置。

**易失分回答：** “rank翻倍就是全模型能力翻倍”“q/k/v/o/up/down就一定包含全部专家”。

来源：[训练参数专题 §3](02_训练参数选择与LoRA技术分层.md)。

## Q28 ★｜请讲清 RL 全流程，以及其中各阶段的显存组成与变化

**主答**

我先区分 Actor、Rollout、Reference 和 RM 四种功能角色，再按它们在设备上的驻留时序分析显存。它们不一定各有一份完全独立权重，也不一定在同一设备池。GRPO 主线通常不需要 PPO 式 learned critic，不能照搬“四模型全驻留”的固定账本。

一轮流程是：取 Prompt 并按 G 生成候选，计算 RM/规则和最终 Reward，得到 old/ref logprob，计算组内优势，再以 current logprob 做多 minibatch 更新，保存并同步 Actor 权重到 Rollout Replica，进入下一轮。

主要峰值可能发生在生成、反向或同步。显存应算“同一时刻实际共存的组件”，而不是把各组件独立峰值全部相加，也不是只取每个模型单独占用的最大值。

**一、先把执行阶段讲完整**

~~~text
装载底座、adapter、tokenizer 和并行配置
→ 初次 Actor → Rollout 权重同步
→ Prompt Batch；同 uid 展开 G 条候选
→ vLLM prefill / decode，保存 Response、mask、版本与采样信息
→ RM scoring + Guard → Composite Reward
→ 取得/重算 old logprob；计算 ref logprob
→ 同 uid 的组均值、标准差与 Advantage
→ minibatch：current forward → policy/KL loss → backward → optimizer
→ 按策略保存 checkpoint
→ 同步新 Actor 权重/adapter 到 Rollout Replica
→ 恢复下一轮生成所需内存
~~~

这是逻辑依赖顺序；独立 GPU Pool 可以让部分 scoring 与 generation 流水重叠。old logprob 在 bypass 模式可直接来自 rollout，decoupled 模式重算。ref和RM只是前向评分角色，不产生Actor反向图，但仍占权重、临时tensor和输出空间。

**二、逐阶段列出同时驻留项**

| 阶段 | 主要驻留与临时分配 | 重点检查 |
| --- | --- | --- |
| 装载/初始化 | 各模型权重或分片、量化元数据、通信组、CUDA context、加载临时副本 | CPU-first或分层加载是否生效；是否出现完整权重瞬时聚集 |
| Rollout prefill | 推理权重、输入处理、Attention workspace、逐步形成的KV | Prompt长度、active sequences、prefill token cap |
| Rollout decode | 推理权重、KV cache、采样/输出buffer、CUDA Graph相关内存 | 活跃并发、生成长度、KV dtype与缓存预算 |
| RM scoring | RM权重、批次前向激活/临时logits、score输出 | 独立还是同卡；是否无梯度；RM自己的模板长度 |
| old/ref logprob | 训练/参考权重、前向临时张量、logits/logprob输出 | microbatch、是否保留不必要的完整词表logits |
| Actor update | 参数分片及gather窗口、adapter梯度、optimizer状态、反向activation、通信bucket | 量化/分片真实dtype、checkpointing、microbatch、token cap |
| Weight sync | 源参数materialization、目标推理权重、传输buffer、可能尚未释放的KV | 新旧副本双持、adapter还是全量同步、唤醒先后 |
| Checkpoint | 状态收集、可能的参数gather、CPU暂存、异步写盘状态 | 保存是否把完整模型聚到某rank；CPU/磁盘是否成为瓶颈 |

对设备 g，可用概念式表示：

$$
M_g^{\mathrm{peak}}=
\max_{\tau}
\left(
M_{g,\tau}^{\mathrm{live}}
+M_{g,\tau}^{\mathrm{cached\ free}}
+M_{g,\tau}^{\mathrm{external}}
\right).
$$

$\tau$ 是执行阶段/时刻。先选定一个统计边界，例如当前训练进程的PyTorch allocator：live只计该allocator内部仍在使用的分配；cached free只计同一allocator保留但当前未使用的空间；external计该边界之外的设备物理占用，例如其他进程、CUDA context或未纳入该allocator的NCCL/vLLM分配。权重、KV、activation与工作区按实际分配归属只计一次；不能先把所有引擎的KV记入live，再将同一笔作为external重复相加。

**三、Rollout 的 KV 怎样估算**

对普通 Transformer、同长度层、KV不共享也不分片的教学情形：

$$
M_{\mathrm{KV}}\approx
2L\,H_{\mathrm{KV}}\,D_h\,b_{\mathrm{KV}}
\sum_{j=1}^{N_{\mathrm{active}}}T_j.
$$

2表示K与V；L是层数；$H_{\mathrm{KV}}$是KV头数，不一定等于query头数；$D_h$是head dimension；$b_{\mathrm{KV}}$是每元素字节数；$T_j$是该活跃序列实际缓存的token数。

教学例：L=32、KV heads=8、head dimension=128、BF16每元素2字节，8条活跃序列各2048 token，得到2,147,483,648 bytes，即2GiB KV。它不代表项目模型的真实KV结构。

实际模型还受GQA/MQA、滑窗/混合Attention、prefix sharing、block分配、TP切分或KV头复制影响，不能一律除以TP，也不能直接套这张均匀层公式。预留KV池可能比实际活跃token占用大。

**四、G、长度、microbatch怎样影响峰值**

G增加首先使总候选与计算工作量增加；只有更多候选同时活跃，才相应提高生成峰值。若调度器把候选排队而不丢弃，总耗时可能增加，但某些阶段峰值仍由active sequences或microbatch控制。

生成KV大体随缓存token数线性增长。训练侧Attention某些实现可能物化平方规模张量，但Flash/Memory-efficient attention不一定保存完整 $T\times T$ 矩阵；不能普遍声称“长度减10%，整个训练显存就减19%”。

microbatch主要约束一次forward/backward的activation峰值；gradient accumulation能保持global batch，但增加顺序执行次数。token packing cap与单样本长度不是一个参数，改变后必须检查是否裁掉业务关键上下文。

**五、为什么4-bit与LoRA不能消除RL显存问题**

4-bit主要描述某条加载路径的权重存储；LoRA减少可训练参数及其梯度/optimizer状态。它们不自动量化KV、logits、activation、通信buffer或所有模型副本。RM使用QLoRA，也不表示Actor训练、reference和vLLM推理都采用同样量化。

30B全量按4bit的裸权重下界是15GB，BF16是60GB；实际还要加量化元数据、高精度模块和其他状态。MoE的激活参数少不代表只存激活专家的参数。

在RL中尤其要看：FSDP Actor shard与vLLM权重/KV是否共卡，唤醒时是否双持，参数同步是否materialize完整模型。仅调低LoRA rank可能触不到真正峰值。

**六、如何安排sleep、offload和同步**

分时驻留的目标是：生成时给rollout留足权重和KV预算，更新时释放不需要的生成内存，同步时尽量延迟KV恢复并控制参数聚集。

vLLM当前文档区分sleep等级：level1备份权重到CPU并丢弃KV；level2丢弃权重与KV，需要重新加载/更新权重。可先只唤醒weights，更新后再唤醒KV。具体wrapper与后端支持仍应按版本检查。[vLLM Sleep Mode](https://docs.vllm.ai/en/latest/features/sleep_mode/)

本地verl的naive同步路径中，先恢复目标rollout weights，再取参数并更新，配置启用时offload Actor，最后恢复KV。这个顺序仍可能在同步中同时持有源参数、目标权重和buffer，不能说“源码调用了sleep，所以任何时刻都不会双驻留”。

[engine_workers.py](../../verl/verl/workers/engine_workers.py)中的update_weights路径与其他checkpoint engine后端不完全相同。同步前确认目标内存已准备；同步后确认版本、adapter/base关系和固定输入logprob/生成行为，再开始下一轮。

**七、现场排查怎么讲**

先在各阶段边界同步并记录峰值、live tensor和进程占用，按相同长度/并发复现。PyTorch allocated是活跃tensor相关占用，reserved包含allocator缓存，不能把二者相加；nvidia-smi还可能包含非PyTorch内存和其他进程。empty_cache不释放仍被tensor引用的内存。[PyTorch CUDA内存管理](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management)

再根据峰值选择动作：

- Rollout KV不足：检查active sequences、Prompt/Response长度、KV预算和dtype。
- backward不足：检查microbatch、有效token、activation checkpointing/offload及参数gather。
- sync不足：检查KV是否提前恢复、全量权重materialization和新旧buffer双持。
- scoring不足：检查RM池与Actor池是否重叠、RM自己的batch与模板长度。
- 没有CUDA OOM却卡住：另查NCCL、CPU内存、共享内存、I/O或同步屏障，不能都当显存不足。

每次只改与假设相关的参数，越过原失败点后还要完成“生成→打分→更新→同步→下一轮生成”。单独跑通一次forward不足以验证RL闭环。

**连续追问**

- **“显存总和超过单卡容量，offload就一定有解吗？”**  
  只有组件能按时释放/搬迁、CPU和带宽也够，并且某个不可分割操作峰值不过卡，才可能有解。8×32GB也不能供某个单卡算子直接申请256GB。
- **“为什么RM用ZeRO-2，Actor却用FSDP？”**  
  RM训练、在线RM推理和Actor更新是不同路径。量化底座能单卡驻留时ZeRO-2可避免参数前向gather；Actor需与rollout协同且底座/精度不同，会采用另一分片与同步方案。选择由模型、拓扑与后端决定。
- **“小microbatch会不会改变训练目标？”**  
  理想正确累积可保持目标batch，但变长样本的loss归一化、最后不足batch和随机算子会影响等价性，要核对实际归一化及步数。

**易失分回答：** “4-bit把所有显存除以4”“G翻倍所有显存必翻倍”“reserved再加allocated就是总占用”“LoRA只训练少量参数，所以反向不经过底座”。

## Q29｜保存成功后，为什么RM重载会失去原来的排序能力？

**主答**

RM产物不只有LoRA A/B，还包括已训练的score head，以及解释输入和分数所需的配置。漏存score.weight，或恢复时重新随机初始化head，会使原本学到的分数失效；底座、tokenizer、chat template、EOS/pad或pooling变化，也可能让同一文本被不同方式评分。

因此保存前后使用固定Pair核对：输入token一致、最后有效位置一致、score head已恢复、raw score数值在约定容差内、偏好方向一致。merge到服务端后再做同样检查；不是看到文件生成或API返回成功就结束。

**连续追问**

- **“推理恢复与精确续训分别需要什么？”**  
  推理需要正确底座、adapter、head和输入/评分配置。续训还需要optimizer、scheduler、global step、随机状态、sampler/DataLoader进度和相关分布式状态；相同loss无法证明精确续训。
- **“只检查方向一致够吗？”**  
  对固定Pair方向必要，但在线Reward还受尺度和clamp影响，所以还检查分数差、分布和最终组合Reward。接近tie的样本尤其敏感。
- **“为什么modules_to_save重要？”**  
  它让额外训练模块随adapter保存。head应在PEFT包装前正确初始化并纳入保存范围；恢复后确认实际tensor，而非只读配置字段。

**易失分回答：** “adapter目录存在，所以模型可部署”“训练能继续就说明恢复状态完全相同”。

来源：[RM-A 正文 §5](../RM/RMv1-v5_从SFT平台到Anchor_RM完整面试复习.md)、[RM-B 正文 §8](../RM/RMv6-v6.6_从Unified_Clean_Attack到定向Hardening完整面试复习.md)。

## Q30｜怎样确定一次运行真正生效的参数，而不是launcher默认值？

**主答**

完整配置是默认值、YAML、环境变量、命令行覆盖和框架运行时归一化共同作用的结果。我会保存解析后的配置、代码版本、底座/adapter/tokenizer hash、数据manifest和设备拓扑，再从日志与产物核对实际执行。

比如统一方案G=6，而存档launcher默认G=4；只有实际解析配置和每uid的候选数能说明这一轮用了哪个值。Prompt Batch、Response Batch、PPO mini batch、microbatch和DP规模必须分别标单位，不能把所有字段叫batch。

对数据并行、完整累积的常见情况：

$$
B_{\mathrm{global}}=W_{\mathrm{DP}}B_{\mathrm{micro}}G_{\mathrm{accum}}.
$$

RM 配置 8×1×8=64 Pair，每步有128个chosen/rejected序列槽位；DP不能直接替换成有TP/PP时的总GPU数。步数算例（上一代 44,280 口径）：44,280/64=691.875；在1个epoch、每Pair恰好遍历一次、无sampler补齐且末批仍更新的理想条件下，共692步，最后56 unique Pair（当前设计 30,000/64 ≈ 469）。真实sampler补齐、drop_last和调度行为以运行记录为准。

**连续追问**

- **“warmup 0.03就是21步吗？”**  
  692×0.03=20.76，整数处理由scheduler实现决定。要记录真实LR序列和总更新预算，不能只报ratio。
- **“同样设置seed就能逐bit复现吗？”**  
  不保证。还受GPU算子、数据顺序、并行拓扑和后端影响。分别定义配置可复现、统计结果可重复与逐bit相同，不把它们混为一谈。
- **“哪些记录最有用？”**  
  解析配置、trainable模块与参数数、输入/监督token统计、每uid候选数、每步LR、样本/Pair/token exposure、checkpoint版本及完成标记。日志不能泄露私有原文或密钥。

**易失分回答：** 拿脚本顶部默认值回答全部运行细节，忽略环境覆盖和框架内部扩展。

## 新增追问（2026-11-08 方案补充：选型、DPO、摘要、部署、置信区间、无成绩怎么讲）

> 以下 6 题对应《完整完善方案_20261108》新增的决策层，回答与主文口径一致；没有实跑结果的部分讲协议与判据，不补历史。

### Q31｜为什么选这个底座？怎么比较才公平？

**主答**：候选集合（Gemma4-26B-A4B IT / Qwen3-30B-A3B-Instruct-2507 / 较小模型 / API+prompt 基线）经 E0–E3 漏斗：运行可行性 → 原始能力 → 受控短训（512 Group、两 LR、复跑 seed）→ 部署复核。公平性三条：同业务信息用各自正确模板；跨 tokenizer 不按 loss 排名，比训练后绝对质量；解码调参给同等预算。未微调表现不是后训练上限，短训排序也不证明 RL 上限；只扩训入选者——要主张「扩训后仍最优」需给次优者对等预算，预算不够就保留结论边界。详见 [模型选型专题](../SFT/00_模型选型与小规模验证.md)。

### Q32｜为什么不直接 DPO？

**主答**：保留最小方法对照——同一起点比较「不更新 / 继续 SFT / DPO」；在线奖励已验证且预算允许时，加短程 RM-guided RL。选在线 RL 的理由：需要在当前策略不断产生的新候选上持续优化、已有可信在线评分、收益足以覆盖采样 + RM + 工程成本。DPO 用固定偏好对直接更新策略、不需要显式 RM，但仍需可靠偏好数据、参考策略和独立评测；不能因为项目叫 RLHF 就跳过更简单的方案。

对照实验的完整协议（GRPO vs GSPO 机制层 + DPO vs 在线路线的两层对照、预算表、预注册判定规则与留空的结果台账）见 [RL/03_算法选型对照实验](../RL/03_算法选型对照实验_DPO_GRPO_GSPO.md)；配套实现在仓库 `training/GRPO_Training_Package/algorithm_selection/`（含 δ 训推诊断脚本、DPO 数据转换与 LLaMA-Factory 配置，均带单测，预注册未执行）。

### Q33｜RM 离线用 raw history、在线用 summary，标签还算数吗？

**主答**：这是显式登记的分布假设，不是已解决的问题。三个低成本对照：摘要保真（同状态 raw vs summary，关键事实是否保留/新增）、RM 输入适配（同 RM 同候选只换上下文视图，看排序翻转与 Judge 标签是否仍成立）、Actor 输入适配（同场景同解码协议比较两种视图行为）。RM 对照用独立 Calibration 50 Pair（Clean 25 + Attack 25）。摘要丢事实修摘要；事实保留但 RM 排错先修在线评分适配；产品若改用「摘要 + 最近几轮」，登记为新的输入协议版本并重新验证，不能默默换格式。

### Q34｜模型怎么上线？出问题先重训吗？

**主答**：三类服务（训练 rollout / RM 打分 / 产品推理）分开；交付单位 = 模型版本 + 输入协议 + 生成配置 + 服务配置，四件一起交付、一起回滚。Serving Parity 六步中第 4 步（真实多轮流程：回复写回会话、摘要刷新、历史截断）是单轮冻结 SR 覆盖不到的，发布前必须执行。出问题按路由：模板/底座/停止标记错误修服务；摘要缺事实修摘要；量化掉质量按部署形态回归；只有分布性不适应才回到训练。详见 [交付与部署专题](../RL/02_模型交付与上线部署.md)。

### Q35｜胜率 55%、「至少两组更优」这些门槛有统计依据吗？

**主答**：都是预注册工程启发式，不是显著性证据。55% 是待校准示例；三组配置共享同一批 Scene 且温度与 top_p 同变，是解码条件稳健性检查，不是三个独立实验。置信区间按 Scene/Family 成组处理，多 seed、多解码配置不能当独立新题；要声明显著，需对同 Scene/Family 做配对重采样并报告差值区间。

### Q36｜RL-B 没有最终成绩，面试怎么讲？

**主答**：讲真实结局与协议，不编结尾。历史真实结局是 v6.10 step90 停线（clean 守住、attack 未压下）；当前设计是针对该结局的重构，成绩待评测，判定协议已预注册（三配置；Win 门 = True Roledrop 下降至少 3pp；三组护栏全守）。RM 层的 60.3%→86.0% / 55.5%→89.5% 是 B6 排序的给定口径，不能推 Actor 破角率或线上收益。敢说「这一步还没跑、协议和判据在这里」本身就是证据纪律的一部分。
