# 00｜模型选型与小规模验证：SFT 之前的前置决策层

> 口径：本文全部内容为 **[当前设计]**，来自《Character-RLHF 完整完善方案_20261108》§4 与《附件母版完善稿》§1.10 的展开；所有实验表为空结果台账，`待填` 表示尚未执行，不代表已实跑。历史项目实际从 Gemma/Qwen 双线开始训练（见仓库 README「SFT 阶段」），本文是把那段经验反推成一个可解释、可复现的选型合同，供面试讲「为什么选这个模型」时使用。
>
> 阅读顺序：本文 → [SFT 完整正文](Character-RLHF_SFT_Canonical_Full.md)。本文只回答「用哪个底座、怎么公平比较、什么时候放弃」；数据工程与训练细节在完整正文。

## 0. 这一层解决什么问题

附件母版 §1.10 直接写死了 Gemma4 与训练配置，缺少「为什么是它」的决策链。面试官的连续追问一定是：

```text
为什么选这个模型？
→ 和谁比过？比较公平吗？
→ 跨模型为什么不按 loss 排名？
→ 小模型为什么不省到底？
→ 部署约束（显存/延迟/成本）进选择了吗？
```

本层的回答框架：**候选登记 → 可行性排除 → 原始能力初筛 → 受控短训 → 部署复核 → 只对入选者扩训**。每一步都写清通过/停止条件，选型本身成为一个可审计的实验序列，而不是一句「我们用了 Gemma4」。

## 1. 候选集合与前置约束

### 1.1 候选表

| 对象 | 纳入理由 | 待检验假设 | 登记状态 |
| --- | --- | --- | --- |
| Gemma4-26B-A4B 的 IT 版本 | 当前方案的工作选择 | 角色质量、适应成本与部署预算之间是否合适 | 精确 revision 待填 |
| Qwen3-30B-A3B-Instruct-2507 | 同量级异家族、已有项目经验（历史 SFT 双线之一） | 是否能改善语言、角色或后训练性价比 | 非思考版本，登记时注明 |
| 较小模型（如 Qwen3-8B） | 成本对照 | 较大模型的增益是否值得额外资源 | 8B 可切换思考模式，比较时不能遗漏 |
| 当前 API + 最佳已知 prompt | 产品基线 | 训练后相对现状究竟改善什么、损失什么 | prompt 版本待填 |

这是与本项目有关的候选集合，不是市场排名或穷举。MoE 模型的激活参数量（每个 token 实际参与的参数）不等于加载权重总量，规划显存时按「实际权重 + KV cache + 运行工作区 + 余量」计算，纸面估算与硬件实测分别记录。

### 1.2 部署前置约束（向部署方取得）

```text
硬件/成本范围          待填
典型输入输出长度        待填
目标并发               待填
首字/完整回复延迟要求    待填
支持的推理栈           待填
```

尚不明确时登记为「部署假设，待验证」，不凭空写成现有生产配置。具体 GPU 张数与服务参数在 E3 部署复核中确定。

## 2. Selection-Dev 与比较协议

### 2.1 评测集

```text
Selection-Dev = 复用已明确作为开发用途的 SR 设计
  Clean 200 Scene + Attack 100 Scene

初筛：Dev 的预先固定子集
正式比较：完整 Dev
```

历史初始选型若尚无 Attack 目标（Attack 是第一阶段 RL 后才明确的），分别写「初始实验」和「后续扩展验证」，不倒写。最终 Actor Test 另留来源家族（见《Benchmark 分层》Final-Test 节），样本量按想检测的改善幅度与不确定性确定，不把 300 Scene 视为普遍充分的标准。

### 2.2 公平性原则

1. **不能看模型回答后删掉它不擅长的题。**
2. 相同业务信息使用各自正确模板；核对角色卡、特殊 token、历史截断和结束标记。
3. 训练数据尽量保持相同语义覆盖；记录不同 tokenizer 的长度与有效监督 token。
4. 共同参考解码配置与实际服务候选配置分别报告；若某模型需要专门解码调参，给同等搜索预算并在 Dev 上完成——不给一个模型更充分的优化机会。
5. **跨 tokenizer 不按训练 loss 排名**（loss 依赖词表与分词，跨模型不可比）；优先比较训练后绝对业务质量，再看相对自身起点的增益。

## 3. 实验漏斗 E0–E5

| 实验 | 操作与产出 | 通过/停止条件 | 下一步 |
| --- | --- | --- | --- |
| E0 运行可行性 | 加载、模板、长输入、生成、LoRA 小步训练、保存重载；得到资源记录 | 关键链路可运行且预算可接受；环境配置错误先排除 | 进入 E1 或淘汰不可行候选 |
| E1 原始能力 | 三个本地候选 + 产品基线在固定题上生成；记录失败切片 | 留下两个值得短训的候选；明确预期可修短板 | 受控短训 |
| E2 短训适应 | 相同数据、相同调参机会；比较绝对业务质量、收益和成本 | 关键护栏不退化，预算内有竞争力 | 暂定底座；接近时补独立样本或保留低成本方案 |
| E3 部署复核 | 导出/重载，用拟部署精度、模板和上下文协议做质量与性能测试 | 服务形态下效果、资源、延迟同时可接受 | 正式 SFT；否则先修部署或重选 |
| E4 正式 SFT | 对选定底座扩大训练，Dev 选 checkpoint | 所选方案在目标规模达到质量、护栏与预算要求 | 进入方法选择或直接交付 |
| E5 最终确认 | 模型与服务配置锁定后评测 Final-Test | 达到预先定义的质量和服务要求 | 灰度；失败则登记后续轮次 |

两条边界：

- **E1 不把未微调表现当后训练上限；短训排序也不能证明 RL 上限。** 对后续 RL 的最小兼容性（LoRA 可训、保存重载、显存可行）在 E0 检查，不必给所有候选训练完整 RM/RL；只有未解决的路线分歧确实取决于 RL 表现时，再补有针对性的对照。
- **只扩训入选模型**能验证该方案是否达标，不能证明短训排序在更大规模仍成立。要主张「扩大训练后仍优于次优模型」，需给关键次优候选对等扩展预算；预算不支持时保留结论边界。正式训练明显偏离短训预期时，重新打开选型判断。

## 4. 第一轮短训预算（启动值）

```text
数据：从训练池分层抽 512 个完整 Group
     每组 6 个监督回答 = 3,072 个监督回答

探索：2 个候选 × 2 个学习率（如 5e-5 与 1e-4）= 4 次短训
复跑：每个候选的最佳 Dev 配置换一个训练 seed = 2 次
合计：6 次短训 + GPU 小时上限（待填）
```

LoRA 从 `r64 / alpha128 / q/k/v/o` 起步，但需核对各候选的实际模块名与可训练参数量——rank 相同不保证训练容量等价。每轮保存：数据清单、mask 检查、长度处理、学习率、seed、token 暴露、耗时、显存。

这是启动预算，不保证统计充分，也不表示所有模型一轮就能调好。发现配置不适合某模型时，给对称的补充预算或限定结论，不能据此宣布模型家族更差。

## 5. 选型决策规则

### 5.1 主指标与分项

```text
主指标：固定场景盲评偏好胜率
  win_rate = (胜 + 0.5 × 平) / 总比较数

分项同时报告：语言、角色、承接、丰富度、密度、破角、生成失败
```

### 5.2 看结果前预注册

在看任何结果之前约定并登记：

```text
最小值得关注的收益        待填
最大可接受退化            待填
成本上限                  待填
追加样本预算              待填
```

此前讨论过的 55% 胜率只能作为**待校准门槛示例**，不是行业标准。置信区间按 Scene/Family 成组计算；多 seed 和多解码配置不能当成独立新题。

### 5.3 平局处理

质量没有可辨别优势时，可以根据成本、兼容性和维护负担做工程选择，写成：

> 在当前预算和评测下暂定采用 X。

不补造显著领先结论。

## 7. 高频追问

1. **「为什么不直接拿最大的模型？」** 先答部署约束与成本上限，再答增益是否值得；较小模型是成本对照，不是凑数。
2. **「为什么不按 loss 比较？」** 跨 tokenizer 的 loss 不可比；比较训练后绝对质量，loss 只做自身优化诊断。
3. **「短训胜出，正式训练一定也胜出吗？」** 不一定；只扩训入选者验证达标，扩训后排序要主张需对等预算。这正是 E4 与 E2 分开的原因。
4. **「选型和数据建设谁先？」** 可以并行：数据合同（Head/Continuation、语言规则）与底座无关；但正式 SFT 规模只在选型收敛后投入。
5. **「历史上真的是这样选的吗？」** 历史是双线都训了再比较（Gemma/Qwen 两条 SFT 线）；本文件把那个过程整理成预注册协议，差异点在于 E0–E5 的门槛是现在补的设计。
